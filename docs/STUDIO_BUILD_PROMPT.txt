Upstage Studio의 노코드 기능으로 시상금 증빙을 검토하고, 문제 서류의 담당자 알림과 팀장 메일 자동 발송에 연결할 결과 및 지급내역 표를 만들어줘.

아래 요구사항에 따라 실제 노드와 설정을 구성해줘. 구현 코드를 작성하는 방식이 아니라 Studio의 노드, 스키마, 검증 규칙, 프롬프트를 사용해줘.
설정과 테스트에는 가상정보로 만든 01·02·03 샘플을 사용한다. 정답지와 사용안내는 입력 문서로 올리지 않는다.

[1. 업무와 처리 단위]

대회에 참가한 각 팀의 팀장이 팀원 전체 정보를 작성하여 다음 서류를 제출한다.
- 01: SW수혜학생 신청 및 시상금 지급 확인서
- 02: 개인정보 수집·이용·제공 동의서
- 03: 팀 대표의 신분증 사본 및 통장 사본

한 팀의 01·02·03을 하나의 케이스로 처리한다.
01에는 대표와 팀원 전체 정보가 있다.
03은 팀 대표의 증빙이므로 대표와 대조한다.
4명씩 5팀이면 케이스 5개, 입력 파일 15개, 전체 학생 표 20명분, 지급대상자 상세내역은 대표 5명분이다. 이 숫자는 예시이며 고정하지 않는다.
파일 하나가 여러 페이지일 수 있으므로 파일 수와 페이지 수를 구분한다.
00번 상금 지급내역서는 학생 제출·추출 입력에서 제외한다. 두 표를 포함한 전체 문서를 결과보고서의 출력 템플릿으로 별도 관리하고 최종 맨 앞에 한 번 배치한다.
실제 출력 양식 파일명은 ‘00. 상금 지급내역서_WAVE 2026.hwp’다.

[2. 최종 결과]

A. 00의 첫 번째 지급상세 표: 대표를 포함한 전체 학생
열 순서: 연번 / 성명 / 학번(학교) / 전공 / 팀명 / 시상구분 / 지원액(원)
기존 출력 키 name / student_id / major / team_name / award_type / support_amount를 유지하고 school을 추가한다.
연번은 최종 학생 행 순서에 따라 1부터 생성한다. 학교는 학번(학교) 셀에 넣고 별도 열을 만들지 않는다.

B. 00의 두 번째 시상금 지급대상자 상세내역: 팀 대표만
열 순서: 연번 / 성명 / 학번 / 전공 / 주민번호 / 은행명 / 계좌번호 / 예금주명 / 지급총액 / 세액 / 차인지급액
출력 키: name / student_id / major / rrn_display / bank_name / account_number / account_holder / gross_amount / tax_amount / net_amount
한 팀당 대표 한 행이며, 연번은 별도로 1부터 생성한다.
rrn_display에는 03의 id_number_display에 있는 마스킹 표기를 그대로 넣는다.
지급총액·세액·차인지급액은 미확인으로 두고 담당자가 입력·확인한다.

C. 팀별 제출 원본 증빙
00 전체를 맨 앞에 한 번 배치하고, 두 표의 확정 팀 순서와 동일하게 각 팀의 01 → 02 → 03을 한 번씩 첨부한다.
4팀의 예: 00 전체 → 1팀 01·02·03 → 2팀 01·02·03 → 3팀 01·02·03 → 4팀 01·02·03.
이는 구성 문서 13개이며 13쪽이라는 뜻은 아니다. 각 문서의 전체 페이지를 보존한다.
팀원이 여러 명이어도 같은 팀의 증빙을 반복하지 않는다.
원본 전체 페이지와 서명·이미지를 유지한다.
최종 제출물은 편집 가능한 HWP/HWPX와 같은 확정 내용의 PDF다.

시상구분과 지원액은 01~03에 없는 정보다.
두 값은 문자열 ‘미확인’으로 출력하고 담당자가 나중에 팀별로 입력한다.
이 두 값의 미확인을 학생 서류 오류나 재제출 사유로 처리하지 않는다.
금액을 추측하거나 미확인을 0원으로 계산하지 않는다.
지급총액·세액·차인지급액 등의 담당자 입력 대기도 학생 서류 오류로 처리하지 않는다.
지원액과 지급총액의 연결·세액·차인지급액 자동 계산은 별도 규칙이 확정되기 전까지 가정하지 않는다.
원본 양식의 세율 안내만으로 세액을 자동 계산하지 않는다.

D. 문제 서류에 대한 담당자 알림과 팀장 결과 메일
확인된 누락·불일치는 발견 즉시 담당자에게 알리고 팀장에게 보완 요청을 자동 발송한다. 판독이 불확실하면 담당자가 원본을 확인한 뒤 팀장에게 결과만 자동 발송한다. 보완본은 같은 팀의 새 제출 버전으로 다시 검토한다.

[3. 워크플로우 구성]

여러 팀이 섞인 일괄 업로드는 서비스가 먼저 같은 대회의 01 명단·제출 근거로 팀을 배정한다. 소속이 불분명하면 서비스에서 담당자가 원본을 확인한다. 백엔드는 파일 목록이 확정된 한 팀의 한 제출 버전만 기존 Agent ID의 판정 Job 한 건에 넣고, job_id로 조회한 판정과 근거를 담당자 화면에 표시한다. Studio 노드를 시험할 때도 같은 팀의 원본 목록으로 한 케이스를 구성한다.

첫 번째: 시상금_팀별_증빙검토
한 팀이 실제로 낸 파일 묶음을 통합 업로드(누락·중복도 받은 구성대로 접수)
→ Parse → Classify(Split) → 문서종별 Extract → Merge
→ Validate → 최종판정 Instruct → 후속 담당자 안내·팀장 안내·지급상세 → Export
판정별 알림과 메일 발송 시점은 [8]을 따른다.

두 번째: 시상금_전체_지급내역표
대회별 최종 결과 컬렉션 Import → Instruct → 00의 두 표 데이터와 최종 첨부 순서 출력

별도의 기준 명부나 수상결과표를 사용하지 않으므로 기본 구성에는 Match를 넣지 않는다.
담당자 검토와 최종 제출 확정은 운영 단계이며 지원되지 않는 자동 승인 노드를 가정하지 않는다.

[4. Parse와 Classify]

Parse:
- 모드 자동, OCR 강제, 한국어, 위치 정보 켬
- 인식이 어려운 샘플은 고급형 또는 DPI 300으로 시험

Classify:
- 문서 분할 후 분류하기
- 파일 단위 분리
- 파일명에 팀명·01·02·03 번호가 없어도 본문의 양식과 작성 내용으로 문서종을 분류한다. 파일명에 팀명이 없다는 이유로 재제출 사유를 만들지 않는다.
- 여러 페이지로 구성된 02 동의서를 한 문서로 유지
- 고정 3페이지 단위로 나누지 않음

문서종:
application_01: 수혜학생 신청 및 시상금 지급 확인서. 프로그램명, 팀명, 대표와 팀원 정보, 지급 확인 내용이 있는 문서.
consent_02: 개인정보 수집·이용·제공 동의서. 안내문과 수혜인력 작성표를 포함하는 문서.
identity_bank_03: 팀 대표의 신분증 사본과 통장 사본을 첨부한 문서.
other: 위 세 종류에 해당하지 않는 문서. 다른 행사 서류나 지급내역서 등.

other도 확인 결과에 남겨 예상 밖 문서가 조용히 제외되지 않게 한다.

[5. Extract 스키마]

문서종별로 다른 Extract를 연결한다.
일반 항목은 String이며 목록을 끈다. 반복 인원은 그룹 테이블을 사용한다.
성명 배열과 학번 배열을 별도로 추출하지 않고 한 사람의 정보를 같은 행에 연결한다.

Extract_01_신청서:
- program_name: 프로그램명
- team_name: 팀명
- representative_name: 대표 성명
- representative_email: 팀 대표 행의 E-mail. 발송 후보 주소로만 추출하고 팀원 주소로 보충하지 않는다.
- representative_bank: 대표 은행명
- representative_account: 대표 계좌번호
- signature_review_notes: 서명 확인이 필요한 위치와 누락 의심 사항. 자유 서술 보조 항목
- members 그룹 테이블: name, student_id, school, major, role, birth_date
  - name: 성명
  - student_id: 학번
  - school: 학교 또는 소속
  - major: 학부 또는 학과
  - role: 대표 또는 팀원
  - birth_date: 신청서에 적힌 생년월일. 현재 00에 없는 생년월일 열을 임의로 추가하지 않음

팀 대표를 포함해 실제 정보가 작성된 사람만 한 행씩 추출한다.
미작성 팀원 칸은 제외한다. 판독할 수 없는 값을 추측하지 않는다.

Extract_02_동의서:
- consent_members 그룹 테이블
  - name: 성명
  - major: 소속 학과
  - collection_consent: 개인정보 수집·이용 동의 표시
  - identifier_consent: 고유식별정보 처리 동의 표시
  - third_party_consent: 제3자 제공 동의 표시
  - signature_state: 서명 흔적 확인 상태

동의 표시 값: 표시됨 / 비어 있음 / 확인 필요
서명 상태 값: 서명 흔적 있음 / 누락 의심 / 확인 필요

실제 인적사항이 작성된 사람만 추출한다.
빈 행에 미리 표시된 체크만 있는 경우 사람으로 세지 않는다.
예시 값이나 안내 문구를 실제 작성자 정보로 사용하지 않는다.
인쇄된 ‘서명 또는 인’ 문구를 실제 서명으로 판단하지 않는다.
시각적 근거가 부족하면 확인 필요로 남긴다.
02에는 학번 칸이 없으므로 학번을 생성하지 않는다.

Extract_03_신분증통장:
- id_name: 신분증 성명
- id_number_display: 신분증에 실제 보이는 주민번호 표기. 앞자리 0, 하이픈과 마스킹 기호를 원문 그대로 보존
- account_holder: 통장 예금주
- bank_name: 통장 은행명
- account_number: 통장 계좌번호
- evidence_issue: 빈 첨부란, 잘린 이미지, 판독 어려움 등

Extract_other:
- document_title: 문서 제목
- description: 문서 설명

공통 지침:
학번, 계좌번호, 주민번호 표시값은 String으로 유지한다.
계좌번호 원문을 보관하고 비교할 때만 공백과 하이픈을 제거한다. 앞자리 0을 보존한다.
마스킹된 주민번호를 생년월일이나 성별로 복원하지 않는다. 가려진 숫자를 추측하거나 원문과 다른 마스킹 기호로 바꾸지 않는다.
주민번호 표시값이 비어 있거나 판독 불확실하면 확인 대상으로 남긴다. 의도된 마스킹 자체는 오류가 아니다.
성명·학과·은행명은 근거 없이 비슷한 명칭으로 바꾸지 않는다.
추출값의 근거를 원본 위치에서 확인할 수 있게 한다.

[6. Merge와 Validate]

네 경로를 Merge에 연결한다.
Validate에는 실제 UI에서 표현할 수 있는 고정 조건을 설정한다.
- 01·02·03이 각각 한 건 존재하는가
- 중복 또는 other 문서가 있는가
- 대표 성명·은행·계좌번호가 비어 있지 않은가
- 01 대표 성명과 03 신분증 성명이 일치하는가
- 01 대표 성명과 03 예금주가 일치하는가
- 정규화한 01·03 계좌번호가 일치하는가
- 01 실제 인원 수와 02 실제 작성자 수가 일치하는가

필수 누락은 보완 대상으로, 판독 불확실성은 담당자 확인 대상으로 남긴다.
복잡한 표의 행별 대응은 Instruct에서 점검한다.
지원되지 않는 조건식이나 필드 참조를 임의로 만들어 넣지 않는다.
시상구분·지원액·지급총액·세액·차인지급액의 존재 여부는 학생 서류 오류 검증에서 제외한다.

[7. 팀별 최종판정과 후속 안내·표 작성]

기존 최종판정 Instruct의 ‘생성하고 결정도 내리기’ 설정과 판정 규칙을 사용한다.
채점 출력은 enum과 reason 두 키만 갖는 JSON이다. enum은 성공 / 담당자확인 / 재제출요청 중 하나, reason은 독립적인 핵심 근거를 담은 한국어 문장이다.
웹 검색은 사용하지 않는다.
Extract 값은 실제 항목 참조 메뉴로 연결한다.

지시사항:
1. 01의 명단을 기준으로 대표와 팀원 전체를 확인한다.
2. 각 인원의 성명·학번·전공 누락을 확인한다.
3. 01과 02의 작성자를 성명·학과로 대조한다. 행 순서 차이는 오류로 보지 않는다.
4. 동명이인이나 표기 차이로 동일인 여부가 불확실하면 확인 대상으로 남긴다.
5. 누락 인원, 추가 인원, 중복 인원을 구분한다. 인원 수만 같다고 명단이 일치한다고 판단하지 않는다.
6. 03은 팀 대표의 정보와 대조한다.
7. reason에 문제가 있는 문서명·항목과 차이를 적는다. 전체 계좌번호·주민번호·주소나 학생용 안내문은 넣지 않는다.
8. 어느 값이 정답인지 임의로 선택하거나 원본을 수정하지 않는다.
9. 서명의 진위를 판정하지 않고 담당자가 확인할 위치를 안내한다.
10. 시상구분과 지원액은 미확인으로 표시하고 학생 오류로 취급하지 않는다.
11. 명확한 필수 서류·기재값·동의 표시·서명·명단 누락이나 실제 문서 간 불일치는 재제출요청이다. 명확한 재제출 사유가 없고 판독·인원 대응·자료 귀속이 불확실하면 담당자확인이다. 요건이 충족되면 성공이다.
12. 원본 목록이 완전할 때만 원본 파일 수를 판정에 사용한다. 3개 미만이면 재제출요청이다. 3개를 초과하면 명확한 재제출 사유가 있는지 먼저 보고, 없으면 담당자확인이다. 파일 수를 알 수 없으면 페이지 수로 대신 판정하지 않는다.

후속 노드는 최종판정과 원문 근거를 받아 아래 자료를 각각 작성한다.
- 담당자 안내에는 팀명, 독립적인 문제 목록과 근거 위치, 대조할 원문값, 확인할 서명 항목을 담는다. 문서 전체가 빠졌으면 접수 파일 목록을 근거로 삼는다.
- 팀장 안내에는 해당 팀의 검토 결과, 문서 번호와 확인된 쪽·행·항목, 필요한 조치와 기존 재제출 경로를 담는다. 기한은 대회에서 정한 경우에만 넣는다. 주민번호·계좌번호·학번·다른 팀 정보와 원본 첨부는 제외한다.
- 지급상세에는 팀원 수, 00 첫 표의 전체 팀원 데이터, 둘째 표의 대표 한 명 데이터를 담는다. 대표 학번·전공은 01에서, 주민번호 표시값과 통장 정보는 03에서 가져온다. id_number_display를 rrn_display로 그대로 옮기고, 은행·계좌·예금주 불일치는 담당자가 원문으로 확인한다. 지급총액·세액·차인지급액은 미확인으로 둔다.

성공은 해당 제출본의 증빙 검사 통과를 뜻한다. 지급 승인은 별도 절차다.

[8. Export, 문제 서류 알림과 팀장 메일 자동 발송]

결과는 대회별 컬렉션으로 구분한다.
다른 대회나 테스트 결과가 최종 집계에 섞이지 않게 한다.
담당자는 원본을 확인하고 보완된 제출본을 확정한다.
추출값을 고친 것과 원본 문서를 고친 것을 구분한다.

재제출·재실행으로 같은 팀 결과가 여러 개 생기면 중복을 표시한다.
최신본을 판별할 명확한 근거가 없으면 임의로 하나를 선택하지 않는다.
추출값 수정이 후속 노드와 컬렉션에 반영되는 방식을 확인한다.
최종 제출본만 집계하는 절차를 실제 Studio 기능에 맞게 안내한다.

접수 기록의 대회·팀·제출 버전과 대회에서 정한 제출 경로를 안내에 연결한다. 팀 배정 확인 중에는 담당자만 원본을 대조한다. 판정 후 다른 팀의 자료가 발견되면 서비스에서 발송·최종 집계를 보류하고 소속을 바로잡은 제출본을 재검토한다. 담당자 알림과 팀장 이메일은 아래 시점에 처리하고, 팀장 메일에는 해당 팀의 확인된 주소를 쓴다.
- 재제출요청이면 즉시 담당자 알림을 만들고, 확인된 모든 보완 사항을 해당 팀장에게 한 통으로 자동 발송한다.
- 담당자확인이면 담당자에게 먼저 원본 대조를 요청한다. 팀장 메일은 담당자가 결론을 기록했을 때만 한 통 자동 발송한다. 이상이 없으면 추가 제출이 없음을, 보완이 필요하면 필요한 서류와 조치를 안내한다.
- 보완본은 기존 묶음에서 해당 파일을 추가·교체하고 중복본을 제외한 새 버전으로 재검토한다. 통과하면 팀장에게 증빙 검토 완료를 알린다. 최초 정상 제출은 예외 알림 대상에서 제외한다.
- 접수 시 대회·팀에 연결해 확인한 팀장 주소 한 개로 보낸다. 01의 representative_email은 수신자 확인에 사용한다. 확인된 주소가 없거나 주소가 불확실·충돌하면 담당자 알림에 발송 보류를 표시하고, 수신자가 확인되면 현재 유효한 결과를 보낸다.
- 대회·팀·제출 버전·안내 종류가 같은 메일은 한 번만 보낸다. 발송 시각·결과를 기록하고 반송·실패는 담당자에게 알려 해결 후 해당 건만 재시도한다. 발송 여부가 불분명하면 이력을 먼저 확인한다. 이전 버전의 대기 메일은 보내지 않는다.
- Studio 실행 오류는 담당자가 재실행할 운영 건으로 기록한다. 학생 메일은 문서 판정이 나온 뒤 그 결과에 따라 처리한다.

시연 환경의 커넥터가 판정 후 자동 발송까지 지원하는지 시험한다. 별도 연동이 필요하면 Agents API 결과를 받아 담당자 알림과 메일 발송 서비스로 넘길 항목과 시점을 제시한다. 문안 생성, 발송 요청, 테스트 메일함의 실제 수신을 각각 확인해 보고한다.

[9. 두 번째 Instruct]

타입: 생성만 하기
입력: 해당 대회의 최종 검토 결과 컬렉션

지시사항:
- 대표를 포함한 모든 팀원을 한 사람당 한 행으로 집계한다.
- 첫 번째 표의 열 순서는 연번 / 성명 / 학번(학교) / 전공 / 팀명 / 시상구분 / 지원액(원)이다.
- 두 번째 표는 팀 대표만 한 사람당 한 행으로 집계하며 [2]의 열과 출력 키를 사용한다.
- 담당자가 확정한 팀 순서를 두 표와 첨부 목록에 동일하게 적용한다. 순서 정보가 없으면 입력 대기로 남기고 임의로 확정하지 않는다.
- 팀별로 묶고 대표를 먼저, 나머지는 01 명단 순서로 배치한다.
- 시상구분과 지원액은 미확인으로 출력한다.
- 지급총액·세액·차인지급액도 미확인으로 출력한다. 담당자가 확인한 값이 별도로 제공되면 그 값을 사용한다.
- 주민번호의 마스킹 표기를 원문 그대로 보존한다. 불일치한 은행·계좌·예금주 값을 임의로 확정하지 않는다.
- 같은 학번이 여러 팀이나 제출본에 있으면 중복을 표시한다.
- 보완 대상 팀이나 동의서 누락 인원을 조용히 제외하지 않는다.
- 예상 팀 수와 학생 수가 주어진 경우에만 비교하고, 부족한 인원을 만들어 넣지 않는다.
- 금액이 모두 확정되기 전에는 각 합계도 미확인으로 표시한다. 양식에 인쇄된 합계 0을 실제 금액으로 사용하지 않는다.
- 00 전체를 맨 앞에 한 번 배치한 뒤, 표의 팀 순서에 맞춰 각 팀의 01 → 02 → 03을 한 번씩 첨부하도록 순서를 작성한다.
- 00 개요의 팀 수·학생 수·지급대상자 수는 실제 집계로 갱신한다. 양식 예시의 6개 팀·13명·지급대상 6명을 고정하지 않는다.
- 행사명은 문서와 대회 설정을 대조하고, 행사 일시·장소 등 근거가 없는 값은 담당자 입력 대기로 남긴다. 서명일을 행사일로 추정하지 않는다.

출력:
- 전체 팀 수, 학생 수, 지급대상 대표 수
- 전체 학생 지급상세 표 데이터
- 대표 지급대상자 상세내역 표 데이터
- 각 표를 Excel에 붙여 넣기 쉬운 탭 구분 텍스트
- 미해결 검토 사항
- 00 전체를 포함한 최종 문서 순서
- 담당자 입력 대기 항목

미해결 사항이나 담당자 입력 대기가 있으면 초안으로 표시한다.
지원액은 팀별 금액이며 팀원 수만큼 중복 합산하지 않는다.

[10. 실제 HWP/HWPX 및 PDF 결과보고서]

Studio의 데이터 Merge와 실제 PDF 페이지 병합을 구분한다.
현재 환경에서 원본 한글 양식 채움, 편집 가능한 한글 문서 결합, PDF 출력이 실제로 지원되는지 확인한다.
지원되면 기능과 설정을 명시한다.
지원되지 않으면 다음을 Studio 밖의 문서 처리 단계로 안내한다. 현재는 서비스 연계 설계안이며 구현 완료로 표시하지 않는다.
- 원본 00 양식 전체를 사용하여 첫 번째 표에는 전체 학생, 두 번째 표에는 팀 대표만 입력
- 학교는 학번(학교) 셀에 배치하고 주민번호는 원문 마스킹 표기를 유지
- 담당자가 시상구분·지원액·지급총액·세액·차인지급액과 그 밖의 미확인 항목 입력·확인
- 실제 인원과 팀 수에 맞춰 표 행·팀별 묶음·개요 집계값 조정. 양식의 13명·6대표 행 수나 2쪽에 고정하지 않음
- 팀별 지원액은 한 번만 합산하고, 각 금액이 확정된 뒤 해당 합계 갱신
- 00 전체 → 확정 팀 순서별 01 → 02 → 03으로 원본 전체 페이지 결합
- 담당자가 검토·확정한 편집 가능한 HWP/HWPX와 같은 내용의 PDF 생성
- 두 출력물의 표 값, 서명·이미지, 페이지 순서와 누락 여부 대조

표 텍스트나 JSON만 생성한 상태를 최종 보고서 생성 완료라고 표현하지 않는다.
PDF 페이지만 병합한 상태를 편집 가능한 HWP/HWPX 생성 완료라고 표현하지 않는다.
담당자가 내려받은 한글을 수정하면 해당 수정본에서 PDF도 다시 생성해야 한다.
원본 서류의 오기입은 추출값 수정만으로 해결되지 않으므로 보완된 제출본을 받아 반영한다.

[11. 구성 후 확인]

먼저 팀별 검토 워크플로우를 만들고 전체 집계 워크플로우를 연결해줘.
실제 노드 연결, 스키마, 검증 규칙, Instruct 프롬프트, 테스트 방법과 별도 처리 단계를 보여줘.
설정 생성과 실제 실행 성공을 구분해서 보고해줘.
정답지를 입력으로 사용하지 않은 상태에서 가상 자료를 실행한 뒤 담당자가 결과를 비교할 수 있도록 해줘.
공식 테스트 입력은 유잇_미션2_테스트set.zip의 팀별 제출 묶음이다. 정상 기대 케이스는 set01(Nextify)과 set02(AutoAI) 두 팀이며 최초 예외 알림은 각각 0건이다. set03의 대표 계좌 불일치와 set10의 동의서 명단 누락은 해당 팀별로 담당자 알림 1건과 테스트 메일함 수신 1통을 확인한다. 같은 버전 재실행 때 추가 발송은 0통, 보완본 통과 후에는 검토 완료 메일 1통이어야 한다.
흐린 사본은 담당자 확인 전 수신 0통, 확인 후 결론에 맞는 메일 1통인지 시험한다. 수신 주소 누락·반송·발송 실패 때는 담당자에게 사유가 표시되고, 해결 뒤 현재 결과만 한 번 수신하는지도 확인한다.
최종판정은 유잇_미션2_answer.json과 대조한다. 학교·주민번호 표시값·대표 지급대상자 상세내역 및 00 전체 편철은 선택된 팀의 원본과 대조한다.
