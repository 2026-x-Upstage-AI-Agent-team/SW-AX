### 담당자 인증과 대회 권한

담당자 계정과 대회 배정은 PostgreSQL에서 관리한다. 대회를 처음 만든 계정만 생성 트랜잭션에서 자동 배정한다. 기존 대회는 운영자가 배정하며 같은 이름으로 재등록해도 권한을 얻을 수 없다. 대회 조회·팀 등록·원본 접수·접수 내역·파일 다운로드에서 서버 세션의 담당자를 사용한다. 원본 SQL은 파일·접수·대회 배정을 함께 조회한다. [계정·권한 관리 명령](../README.md#담당자-계정과-대회-권한)

| 요청 | 동작 |
|---|---|
| `GET /api/auth/session` | 현재 `login`(비로그인은 null)과 `csrf_token`을 받는다. |
| `POST /login` | 같은 쿠키로 폼 필드 `username`, `password`와 `X-CSRF-TOKEN`을 보낸다. `Accept: application/json`이면 성공 204, 잘못된 자격증명은 401이다. 로그인 후 세션을 다시 조회해 새 토큰을 받는다. |
| `POST /logout` | 세션 쿠키와 CSRF 토큰으로 로그아웃한다. 이전 세션 쿠키로 보호된 API를 호출하면 401이다. |
| 원본 URL 직접 요청 | 해당 대회 담당자는 200과 원본을 받는다. 다른 담당자는 미존재 파일과 동일한 404, 비로그인은 401이며 응답에 다운로드 파일명이 없다. |

API 클라이언트의 쓰기 요청은 세션의 CSRF 토큰을 헤더에 보낸다. 기존 접수 화면의 동일 출처 API 요청은 브라우저가 설정하는 `Sec-Fetch-Site: same-origin`으로 판별한다. 로그인·로그아웃에는 CSRF 토큰을 사용한다.

2026년 11월 8일, Chrome에서 두 담당자가 같은 원본 주소를 직접 열어 배정된 담당자만 파일을 받는 것을 확인했다. 별도 시험 DB에서는 로그인 상태를 유지한 채 두 번째 담당자에게 권한을 주자 다운로드가 가능해졌고, 회수 직후에는 같은 주소가 404를 반환했다. PostgreSQL 통합 시험 7건에는 두 계정이 서로의 대회 원본에 접근하는 경우와 공식 ZIP 29개 파일의 SHA-256 대조가 포함된다.

### 원본 수동 배정 API

`GET /api/intake-batches/{id}`로 접수의 `revision`과 원본별 `item_id`, `state`, `team`, `reason`을 조회한다. 기존 접수를 포함해 첫 배정 전에는 `revision`이 0이며 원본은 `unassigned`, 팀은 `null`이다. `batch.target_team_id`는 접수할 때 입력한 출처이며 원본별 배정 결과는 `files[].team`에 담는다.

| 작업 | 요청 | 결과 |
|---|---|---|
| 배정·재배정 | `PUT /api/intake-batches/{id}/files/{item_id}/assignment` | `action`은 `assign`, `team`은 같은 대회의 팀 UUID, `reason`은 앞뒤 공백을 제거한 2~500자, `revision`은 조회한 접수 버전이다. 변경 시 `200 {"saved":true,"revision":1}`처럼 새 버전을 돌려준다. |
| 후보 제외·보류 | 같은 `PUT`에 `action: "hold"`, `exclude: [팀 UUID, …]`, `reason`, `revision` | 원본을 `unassigned`로 남긴다. `exclude`는 같은 대회에서 관련성을 배제한 팀의 전체 목록이며 빈 배열로 제외를 해제할 수 있다. 접수 상세의 `files[].excluded`로 다시 읽는다. |
| 대상 외 | 같은 `PUT`에 `action: "outside"`, `reason`, `revision` | 원본은 `outside`로 보관하고 모든 팀의 확정 대상에서 뺀다. 나중에 원본을 대조해 다시 배정할 수 있다. |
| 원본별 이력 | `GET /api/intake-batches/{id}/files/{item_id}/assignment/history` | 변경 순서대로 `item_id`, `revision`, 전후 팀, `actor`, `reason`, `changed_at`, 결정 후 `state`, `excluded`를 반환한다. 첫 배정의 이전 팀은 `null`, 결정 전에는 빈 배열이다. |

같은 담당자의 직전 요청을 그대로 재전송하거나 현재 버전에서 이미 배정된 팀을 다시 선택하면 이력을 추가하지 않는다. 다른 담당자가 먼저 수정해 버전이 달라지면 `409`를 받고 접수를 다시 조회한다. 대회 권한이 없거나 다른 접수의 원본을 지정하면 `404`, 대회 밖의 팀이나 유효하지 않은 사유를 보내면 `422`다. 처리자는 로그인 세션의 ID이고, 변경 시각은 PostgreSQL이 기록한 시간대 포함 시각이다. 팀 선택, 이력 저장, 접수 버전 증가는 한 트랜잭션에서 처리한다.

2026년 11월 9일, 이전 버전에서 접수한 공식 set01 원본을 시험 대회에서 `staff-a`가 Nextify에 배정하고 `staff-b`가 AutoAI로 재배정했다. 서버를 재시작한 뒤에도 두 이력의 팀·담당자·사유·시각, 최종 팀과 원본 SHA-256이 일치했다. PostgreSQL 통합 시험 10건에는 동시 배정 충돌과 다른 대회의 원본·팀 거부가 포함된다. [접수 API 통합 시험](../tests/test_intake_postgres.py)

### 팀별 제출본 확정 API

| 작업 | API | 결과 |
|---|---|---|
| 팀 제출본 확정 | `PUT /api/intake-batches/{id}/teams/{team}/submission`, 본문 `{"revision": 3}` | 접수 전체 판독·배정 처리가 끝나면 해당 팀 원본을 선택 순서대로 확정하고 `team`, `state`, `submission_id`, `version`, `status_url`을 반환한다. 판독 중이거나 배정 파일이 없거나 해당 팀 후보인 미배정 원본이 남으면 409다. |
| 접수별 확정 결과 | `GET /api/intake-batches/{id}`의 `teams[]` | 팀별 최초 확정 후 결과가 나타난다. `confirmed`는 현재 유효한 목록, `blocked`는 미배정 확인 대기, `empty`는 배정 원본 0건이다. 보류·빈 목록에는 제출본 링크가 없다. |
| 버전별 원본 조회 | `GET /api/submissions/{submission_id}` | 대회 담당자만 확정 버전·상태·생성 담당자와 시각·원본별 접수번호·항목 ID·순서·SHA-256을 읽을 수 있다. 이전 버전의 원본 목록도 그대로 조회된다. |

같은 대회·팀의 최신 버전과 파일별 SHA-256 목록을 정렬해 비교한다. 파일명이나 업로드 순서가 달라도 내용과 부수가 같으면 기존 제출본 ID와 버전을 재사용한다. 문서가 한 부 더 들어오거나 내용이 달라지면 새 버전이다. 접수가 달라도 이 규칙을 적용하며, 버전의 원본 순서는 처음 확정한 순서를 보존한다.

워커가 새 접수의 원본을 판독하면 배정 근거가 확정된 팀의 제출본을 자동 확정한다. 담당자나 기존 API 클라이언트도 팀별로 확정을 요청할 수 있다. 이후 해당 접수에서 배정을 고치면 같은 트랜잭션 안에서 이미 확정한 팀들을 다시 확인한다. 소속이 바뀐 양쪽 팀 중 파일이 남고 목록이 달라진 팀만 새 버전을 받는다. 마지막 원본을 옮긴 팀은 `empty`가 된다. 미배정이 다시 생기면 관련 팀은 `blocked`가 되고, 보류를 풀어 파일 묶음이 같으면 기존 버전이 다시 유효해진다.

같은 팀의 다른 접수를 확정하면 새 접수가 현재 배정의 기준이 되고 이전 접수의 연결은 `superseded`가 된다. 이전 접수에서 같은 최신 버전을 재조회할 수 있으며, 그 팀의 과거 배정을 바꿔 현재 확정을 덮으려는 요청은 409다. `confirmed`는 워커에 전달할 원본 목록이 정해졌다는 뜻이다. Studio 실행과 결과 처리는 별도 단계다.

2026년 11월 9일, PostgreSQL 16에서 공식 set01·02·04의 원본을 3·3·2개로 확정하고 Nextify 원본 한 개를 AutoAI로 옮겼다. 재배정 후 원본 수는 2·4·2개, 버전은 v2·v2·v1이었다. 3팀(set04)은 제출본 ID도 같았다. 다른 접수에서 파일명을 바꾸고 순서를 바꿔 동시에 확정해도 같은 ID가 돌아왔고, 중복 원본 한 부를 빼면 새 버전이 생겼다. 기존 수동 배정 이력의 DB 이관, 서버 재시작 후 확정값 유지와 HTTP 통합시험 15건을 확인했다. ### 팀 제출본 판정 작업 등록·조회

팀을 최초 확정하거나 재배정으로 새 제출 버전을 확정하면 같은 PostgreSQL 트랜잭션에서 판정 작업 한 건을 등록한다. `submission_id`에 고유 제약을 두어 같은 버전을 다시 확정하거나 다른 접수에서 재사용해도 `review_job_id`와 등록 시각을 보존한다. 기존 DB를 이관할 때는 현재 확정된 버전부터 등록한다.

| 동작 | 요청 | 응답 |
|---|---|---|
| 등록 확인·재요청 | `PUT /api/submissions/{id}/review-job` (본문 없음) | 현재 확정본이면 동일한 작업과 200. 보류·빈 목록·교체된 버전을 지정하면 409 |
| 대회별 작업 목록 | `GET /api/events/{event}/review-jobs` | 등록 시각·작업 ID 순서로 반환한다. `state`로 `queued`, `running`, `done`, `failed`, `blocked`, `superseded`를 필터링할 수 있다. |
| 작업 상세와 입력 | `GET /api/review-jobs/{review_job_id}` | 대회·팀·제출본 ID·버전·작업 상태·등록 시각·`submission_url`을 반환한다. 이 주소의 `files[]`에는 확정 순서·SHA-256·`original_url`이 있어 같은 버전의 원본을 내려받을 수 있다. |

담당자 인증과 대회 권한을 적용한다. 등록 재요청은 쓰기 요청의 CSRF 규칙을 따른다. 작업 상세에는 로컬 작업 번호 `review_job_id`, 연결된 Studio 실행 번호 `studio_job_id`, 최근 워커 `worker_id`, 완료 시각 `finished_at`과 저장한 `result`가 포함된다. 대회 목록은 최종판정 `verdict`까지 요약한다.

배정이 다시 보류되거나 원본이 0개가 되면 해당 작업은 `blocked`가 된다. 진행 중인 워커 배정은 회수한다. 같은 제출본이 다시 유효해지면 미완료 작업은 같은 번호로 대기하고, 이미 저장한 결과가 있으면 해당 종료 상태를 유지한다. 다른 버전이 확정되면 이전 작업은 `superseded`로 조회되고 새 버전의 작업만 대기 목록에 들어간다.

React 접수 상세는 `GET /api/intake-batches/{id}`의 `teams[].review_job`에서 작업 번호·상태를 읽는다. 대기 또는 처리 중인 팀이 있으면 3초마다 다시 조회한다. 담당자는 팀별 제출 버전, 처리 실패 여부, 검토 완료 시 최종판정을 확인할 수 있다. 제출본 상세에도 같은 `review_job`이 포함된다.

2026년 11월 9일 PostgreSQL 16의 HTTP 통합시험 16건을 통과했다. 동일 버전 등록을 동시에 4회 요청했을 때 작업 ID와 등록 시각은 하나였다. 공식 set01·02·04를 확정한 뒤 Nextify 원본 한 개를 AutoAI로 옮기자 세 팀의 현재 버전은 v2·v2·v1, 작업은 대기 3건·이전 버전 2건이었다. 작업 저장 실패를 재현했을 때 파일 배정·제출 버전도 함께 롤백됐고, 재시작 뒤 작업 ID와 순서가 유지됐다. Chrome에서 재배정, 보류, 같은 ID로의 대기 복귀가 화면에 자동 반영되는 과정과 모바일 폭 390px의 표시를 확인했다. [통합시험](../tests/test_intake_postgres.py)

### 워커 판정 작업 배정과 결과 등록

서버와 신뢰하는 워커 프로세스에 같은 비밀값 `AWARDS_REVIEW_WORKER_TOKEN`을 환경 변수로 설정한다. 이 자격은 여러 대회의 대기열을 처리할 수 있다. 모든 워커 요청에 `Authorization: Bearer <값>`을 사용한다. 값이 비어 있거나 맞지 않으면 401이다. 배정 응답으로 받은 `claim_token`은 해당 작업의 후속 요청에만 `X-Claim-Token` 헤더로 보낸다.

| 순서 | 요청 | 동작 |
|---|---|---|
| 1. 배정 | `POST /api/worker/review-jobs/claim` | 본문 `{"worker_id":"review-1"}`. 선택 항목 `event_id`로 한 대회를 지정할 수 있다. 가장 먼저 등록된 배정 가능 작업 한 건을 잠가 배정한다. 200이면 `review_job_id`, 팀·제출본·버전, `files[]`, `attempt`, 토큰·만료 시각·기존 Studio ID를 받는다. 현재 가져갈 작업이 없으면 본문 없이 204다. |
| 2. 원본 받기 | `GET {files[].original_url}` | 유효한 배정 토큰으로 그 제출 버전에 포함된 원본을 받는다. 파일마다 순서·이름·바이트 수·SHA-256이 함께 제공된다. |
| 3. 배정 연장 | `PUT /api/worker/review-jobs/{id}/lease` | 본문 `{}`로 연장한다. Studio가 실행 번호를 반환하면 즉시 `{"studio_job_id":"…"}`를 보내 저장한다. 응답은 `lease_until`과 `studio_job_id`다. 이미 연결한 ID를 교체하거나 다른 제출본에 재사용하면 409다. |
| 4. 결과 등록 | `PUT /api/worker/review-jobs/{id}/result` | 완료는 `{"state":"done","studio_job_id":"…","verdict":"재제출요청","reason":"02 동의서 누락"}` 형식이다. 추출 항목은 선택적인 JSON 객체 `output`으로 전달한다. 허용 판정은 `성공`, `담당자확인`, `재제출요청`이다. 기술 실패는 `{"state":"failed","reason":"PDF 변환 실패"}`로 기록한다. 이미 저장한 Studio ID는 본문에서 생략할 수 있다. |

임대 시간은 기본 300초이며 서버의 `AWARDS_REVIEW_LEASE_SECONDS`로 조정할 수 있다. 워커는 만료 전에 배정을 연장한다. 만료된 작업은 다른 워커가 새 토큰으로 가져간다. 이때 `attempt`가 증가하고 이미 기록한 Studio 실행 ID가 돌아온다. 재배정받은 워커는 이 ID로 원격 조회를 이어간다. 두 번째 이후 배정에서 실행 ID가 비어 있으면 기존 원격 요청의 접수 여부를 Studio 실행 이력에서 확인한 후 진행한다.

결과 저장과 종료 상태 변경은 같은 트랜잭션에서 이뤄진다. 같은 토큰으로 같은 결과를 재전송하면 최초 완료 시각을 보존하고 204를 반환한다. 다른 결과, 만료·회수된 배정, 교체된 제출본에 대한 등록은 409다. 필수 판정·사유 등 본문 값이 잘못되면 422다. 대기열의 동시 배정은 PostgreSQL `FOR UPDATE … SKIP LOCKED`로 처리한다.

2026년 11월 9일 PostgreSQL 16과 Spring Boot에서 HTTP 통합시험 21건이 통과했다. 대기 작업 한 건에 두 워커를 동시에 보내 200 한 건과 204 한 건을 받았으며, 두 팀이 대기할 때는 각각 다른 작업을 받았다. 15초 시험 임대가 만료된 뒤 새 워커는 저장된 Studio 실행 번호를 이어받고, 이전 토큰으로 보낸 결과는 409가 됐다. Chrome에서는 공식 set04·set02 원본 접수에 워커 시험 응답을 보내 대기·처리 중·검토 완료(재제출요청)·처리 실패가 수동 새로고침 없이 표시되는 것을 확인했다. 결과와 종료 상태는 서버 재시작 후에도 유지됐다. [HTTP 통합시험](../tests/test_intake_postgres.py)

### 운영 보고서 출력

1. Spring Boot가 담당자가 선택한 팀 순서·제출 버전·지급정보를 보고서 버전에 기록한다. 오픈소스 생성기는 이 값으로 편집 가능한 HWPX를 만들고, Spring Boot는 PDF 출력 요청을 그 파일과 연결한다.
2. 전용 PC의 워커가 Spring Boot API에서 작업과 해당 HWPX를 받아 한 건씩 한글로 출력하고, PDF와 처리 결과를 같은 보고서 버전에 반환한다. 출력이 중단되면 저장된 HWPX로 재시도한다. 이전 요청이 늦게 완료돼도 그 PDF는 요청 당시 버전에만 연결한다.
3. 담당자가 HWPX를 직접 수정해 올리면 그 파일을 새 보고서 버전으로 보관하고 PDF를 다시 출력한다. React는 해당 담당자가 확정한 버전의 두 파일을 함께 제공한다.

**set01·02 실측.** 오픈소스 합본을 한글 2024로 출력한 11쪽(지급내역 2쪽 + 증빙 9쪽)은 120dpi에서 기존 기준본과 모두 일치했다. 시상구분 셀의 수정·저장과 PDF 반영도 확인했다. Linux의 LibreOffice + H2Orestart는 HWPX를 재저장한 뒤 18쪽으로 출력해 서명과 본문이 갈라졌고, rhwp는 10쪽으로 출력해 동의서 안내문이 인쇄 영역 밖으로 밀렸다. [기획서의 출력 방식 비교](../PROJECT_PLAN.md#운영판-출력-방식-비교)

운영 배포 전 학교 계약에서 한글 무인 자동화의 이용 범위를 확인한다. 두 담당자가 각자 발행한 같은 버전의 한 쌍을 받는 과정은 운영판에서 확인했다. 학교 전용 PC의 실제 부팅과 설치 계정의 자동 한글 실행은 현장에서 확인한다. [한컴 한글 오토메이션 이용 안내](https://developer.hancom.com/hwpautomation)

## 1. 업로드 요청과 결과 조회

| 서비스 API | 담당자에게 보이는 동작 | 서버의 책임 |
|---|---|---|
| `POST /api/intake-batches` | 대회를 선택하고 여러 팀의 파일을 함께 올린다. 한 팀에서 받은 묶음은 팀을 지정할 수 있다. 전송 후 `202 Accepted`와 일괄 접수번호를 받는다. | 일괄 접수·파일 항목·원본을 한 트랜잭션에 기록한다. 본문에 `batch_id`, `status`, `status_url`을 넣고 `Location`에도 같은 조회 주소를 준다. |
| `GET /api/intake-batches/{id}` | 팀별 배정 파일, 후보와 근거, 미배정 수, 해당 팀의 검토 진행 상태를 본다. | 각각의 원본에 고유한 `item_id`를 부여해 이름이 같은 파일도 따로 표시한다. 목록이 확정된 팀에는 해당 `submission_id`와 조회 주소를 연결한다. |
| `PUT /api/intake-batches/{id}/files/{item_id}/assignment` | 원본을 대조해 팀을 지정하거나, 관련 없는 후보만 제외하고 파일을 미배정으로 남기거나, 대회 대상 외로 처리한다. | 같은 대회의 팀만 허용하고 각 결정의 근거와 이력을 저장한다. 같은 결정을 재전송해도 작업이나 버전이 늘어나지 않으며, 열어 본 뒤 다른 변경이 있으면 최신 목록을 다시 보여준다. |
| `GET /api/submissions/{id}` | 화면을 다시 열어도 같은 접수번호로 단계·마지막 갱신 시각·오류와 다음 조치를 확인한다. 완료되면 판정과 근거를 본다. | DB에 저장된 처리 상태와 결과를 반환한다. 화면을 열어 둔 동안 대기·처리 중인 건은 3초마다, 지연·운영 확인 건은 15초마다 조회한다. 완료·실패한 건은 자동 조회를 끝낸다. |
| `POST /api/submissions/{id}/retry` | 원인을 해결한 담당자가 기존 접수에서 처리를 재개한다. | 저장된 실패 단계와 `job_id`를 확인해 재개 가능한 작업을 한 번만 예약한다. 실행 중이면 기존 상태를 돌려준다. 원본이 바뀌었으면 보완본을 새 제출 버전으로 접수한다. |

화면은 일괄 접수를 시작할 때 요청 키(`Idempotency-Key`)를 한 번 만들고 전송 재시도에도 재사용한다. 서버는 업로드한 각 파일의 이름·순서·크기를 선택 목록과 대조하고 SHA-256을 계산한다. 파일의 고유 ID·표시명·원본 바이트(`bytea`)를 접수와 같은 PostgreSQL 트랜잭션에 보관한다. 중간 오류는 접수 전체를 롤백한다. 접수 내역을 조회할 때 원본 바이트는 읽지 않는다.

세 파일을 선택하고 마지막 파일 전송이 끊기면 전송 실패를 표시하고 같은 키로 다시 보낸다. 응답만 유실됐으면 기존 일괄 접수번호를 돌려준다. `202`까지 걸리는 시간에는 원본 전송과 로컬 저장 시간이 포함된다. 한글 변환·팀 배정·Upstage 판정·메일 발송은 그 뒤에 실행한다. [HTTP 202 의미](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)

### 1.1 파일 판독과 팀별 제출본 확정

1. **배정할 근거를 읽는다.** 일괄 접수 안의 파일별로 검토용 PDF를 만들고, 텍스트와 표를 읽는다. 이미지에만 있는 근거는 해당 파일에서 OCR로 읽고 쪽과 행을 보관한다. 팀 후보는 같은 대회의 기존 접수와 이번 접수의 모든 01을 먼저 읽어 만든다. 01 본문의 팀명·대표로 팀을 식별하고 전체 명단을 저장한다. 이름 일부의 유사도나 OCR 추정값만 남으면 원본 확인 대상으로 둔다.
2. **한 팀으로 소속이 확인되는 파일을 배정한다.** 담당자가 원접수를 확인해 지정한 팀을 우선하되, 표시된 팀명이나 본문에서 소속 근거가 충돌하면 보류한다. 혼합 02는 모든 작성 행을 읽어 순서와 관계없이 01 전체의 성명·인원수와 대조한다. 두 명 이상이 전원 일치하고 각 성명이 대회 명단에서 유일하면 학과 표기가 달라도 배정한다. 일부 명단 또는 동명이인은 서로 다른 작성자 두 명 이상의 성명·학과가 행마다 한 팀으로만 대응해야 한다. 한 명만 있으면 정확한 팀명 근거도 필요하다. 혼합 03은 정확한 팀명과 신분증 성명이 01의 팀명·대표와 일치해야 한다. 파일명 또는 본문의 팀명은 구분된 전체 표기로 대조하고 부분 일치는 후보로만 표시한다. 계좌·주민번호를 팀 간 검색 키로 사용하지 않는다.
3. **미배정 파일을 해결한다.** `팀 배정 확인`에는 원본 쪽, 후보 팀과 일치·충돌 근거를 보여준다. 후보가 없거나 여러 팀이면 담당자가 원접수와 대조한다. 후보 A·B가 남으면 두 팀을, 후보를 좁힐 근거가 없으면 같은 일괄 접수에서 아직 관련성을 배제할 수 없는 팀을 보류한다. 관련이 없다고 확인한 팀은 먼저 진행한다. 01이 없더라도 제출 출처로 팀을 확인하면 받은 02·03을 그 팀에 접수할 수 있다. 두 팀이 섞인 한 파일은 분리된 원본을 확보할 때까지 보류한다.
4. **팀별 판정 작업을 연다.** 일괄 접수의 모든 항목을 판독했고 해당 팀에 속할 수 있는 미배정 파일이 없으면 파일 목록을 확정한다. 같은 트랜잭션에서 팀의 현재 제출 버전과 판정 대기 작업 하나를 기록한다. 배정된 02가 두 부면 두 부 모두, 실제로 02를 받지 않았다면 01·03만 전달한다. Studio가 제출본 안에서 본문으로 01·02·03·기타를 분류하고 누락·중복을 검토한다.
5. **배정을 고친다.** 변경 전후 팀 ID, 원본 항목, 근거, 처리자와 시각을 남긴다. 판정 후에 잘못된 소속이 드러나면 관련 팀들의 발송 대기·최종 집계를 보류한다. 파일 목록이 바뀐 팀만 새 버전으로 검토하고, 이미 발송한 건은 담당자에게 이력을 표시한다. 소속을 확인하지 못한 원본은 담당자 목록에 남긴다.

팀 목록에서 한 팀을 열면 왼쪽에 원문, 오른쪽에 서류별 체크리스트를 표시한다. 항목은 원본 항목 ID와 쪽·행으로 연결하고, 서류 전체 누락이면 확정 파일 목록으로 연결한다. 화면은 파일의 배정 상태, Studio의 `성공 / 담당자확인 / 재제출요청`, 메일 발송 상태를 각각 표시한다. 담당자는 `담당자확인`의 원본 대조 결과와 최종 제출 버전을 기록한다. [기획서의 단계별 화면](../PROJECT_PLAN.md#44-담당자-화면에서-하는-일)

근거 버튼마다 해당 검토 PDF의 쪽을 열고, 작성 행이 있으면 파일명 옆에 행 번호를 표시한다. 같은 종류의 서류를 여러 부 제출하면 버튼에 몇 번째 원본인지 표시한다. 누락 항목의 **확정 파일 목록 보기**는 열어 둔 제출 버전의 파일만 확정 순서대로 보여준다.

## 2. 팀별 대기열과 중복 처리

- **후속 처리 순서** — 접수 후 원본을 배정하고 팀별 목록을 확정하면 운영판 API가 제출 버전당 판정 작업 하나를 등록한다. 워커는 현재 확정본의 대기 작업을 선점하고, 원격 조회가 중단되면 저장한 실행 ID로 이어간다.
- **동시 실행** — 이 PC가 생성해 아직 종료를 확인하지 못한 Upstage Job은 최대 1건으로 둔다. 다른 팀은 계속 접수할 수 있다. 원격 Job이 끝나면 다음 팀을 시작하며 담당자의 원본 확인이나 팀장 메일의 재시도를 기다리지 않는다. 시연판의 검토용 PDF 변환은 한 번에 한 파일을 처리한다. 운영판의 전용 Windows PC도 최종 HWPX를 한 건씩 한글로 출력한다.
- **동일 제출** — 같은 요청 키와 같은 업로드에는 기존 일괄 접수번호를 반환한다. 처리 중이면 `202`, 완료했으면 `200`과 저장된 상태를 준다. 같은 키를 다른 대회·지정 팀·파일 목록(표시명 포함)에 쓰면 `409 Conflict`로 알린다. 다른 일괄 접수더라도 배정 후 같은 대회·팀의 현재 파일 묶음과 같으면 기존 팀별 제출 버전에 연결한다. 요청 키와 대회·팀·제출 버전에 각각 고유 제약을 두고, 중복 확인과 등록을 한 쓰기 트랜잭션에서 처리한다.
- **비교 단위** — 파일별 SHA-256을 정렬한 **목록**으로 묶음을 비교한다. 같은 파일이 두 번 있으면 해시도 두 번 남긴다. 실제 입력은 선택 순서와 파일 수를 보존하고, 문서종 중복은 Studio가 내용을 분류해 찾는다. set05의 기대 사례인 02 두 부·03 미제출도 검토할 수 있다. 파일명이 같아도 내용이 바뀐 보완본은 새 버전이고, 다른 팀이나 대회의 제출은 별도 건이다.
- **보완본 도착** — 기존 요청에 대한 보완으로 팀과 이전 제출 버전을 연결한다. 예를 들어 02만 다시 받으면 기존 01·03과 새 02로 새 버전을 만든다. 어느 원본을 교체하는지 불분명하면 담당자가 정한다. 이전 버전이 대기 중이면 실행 대상에서 빼고, 이미 시작한 Job은 같은 ID로 종료까지 조회해 이력에 남긴다. 판정 저장·메일 발송 전에 현재 버전을 확인한다.

## 3. 판정 워커의 실행 흐름과 시간 제한

워커는 `파일별 검토용 PDF 준비·배정 → 팀별 목록 확정 → 팀별 판정 Job 생성 → 결과 조회 → 결과 저장` 순서로 진행한다. 작은 PDF 시연은 기획서 10.3절에서 확인한 원래 파일명·`file_data` 직접 첨부 경로를 사용한다. 별도 파일 등록 경로는 접근 권한 검증 후 켜고 등록된 `file_id`를 재사용한다. 단계, 원본 항목, 생성 요청 시각, `job_id`, 실패 횟수와 다음 시도 시각을 DB에 기록한다. 워커는 PC에서 단일 인스턴스 잠금을 얻어 기존 작업을 복구하고, `job_id`가 있으면 같은 결과 조회부터 이어간다. 완료 응답을 받고 DB 저장에 실패해도 같은 ID로 결과를 복구한다.

Job 생성 직전에 ‘생성 요청 중’을 DB에 기록하고 이때부터 동시 실행 1건에 포함한다. 요청 전송 뒤 타임아웃·연결 끊김·프로세스 종료로 응답 ID를 잃으면 ‘실행 여부 확인 필요’로 표시한다. 담당자는 Studio 모니터링에서 설정 버전·파일·요청 시각으로 기존 Job을 찾아 연결하거나, 생성되지 않았음을 확인한 뒤 재개한다. 확인 중에는 새 Job 생성을 보류하되 후속 팀 접수와 저장된 결과 조회는 계속한다. ## 4. 오류 안내와 재시도

| 상황 | 담당자 화면과 복구 동작 |
|---|---|
| 지원하지 않는 형식, 손상·암호로 열 수 없는 파일 | 해당 파일과 조치를 표시한다. 예를 들어 “03 파일을 열 수 없습니다. 암호가 해제되고 열리는 파일로 교체해 주세요.” 접수 전 형식 오류는 `415`, 접수 후 발견한 손상은 해당 건의 처리 실패로 기록한다. 같은 바이트로 자동 재시도하지 않는다. |
| 네트워크 단절, 일시적 429·5xx | 등록 실패가 확인된 파일은 해당 항목만, 상태 조회는 같은 `job_id`로 다시 요청한다. 최초 시도 외에 연속 최대 3회, 기본 2·4·8초의 지수 백오프에 짧은 무작위 지연을 더한다. `Retry-After`가 있으면 그 시각보다 일찍 호출하지 않는다. 한도에 이르면 원인·횟수·재개 방법을 표시한다. Job 생성 요청은 미접수가 확인된 경우에만 재시도하고, 응답이 불명인 경우 3절을 따른다. [HTTP 429](https://www.rfc-editor.org/rfc/rfc6585.html#section-4) |
| 인증·권한 오류, 크레딧 소진 | 담당자에게 조직 키·사용량을 확인할 위치를 안내하고 신규 Upstage 실행을 보류한다. 원인이 해소되면 기존 대기열에서 이어간다. |
| 원격 Job이 `failed`로 종료되거나 결과 형식이 잘못됨 | `job_id`와 실패 단계를 보존한다. 판독·파싱 문제는 원본을, 서비스 장애는 실행 이력을, `completed`인데 `최종판정`이 없거나 규격에 맞지 않으면 노드 출력을 확인한다. 일시적인 장애로 실패 종료된 Job을 담당자가 재실행하면 이전 시도와 새 ID를 같은 접수에 기록한다. 결과 재조회로 복구할 수 있으면 기존 ID를 사용한다. |

로컬 처리 상태는 `대기 → 처리 중 → 완료`를 기본으로 하고 장애 시 `재시도 대기`, `운영 확인`, `처리 실패`를 사용한다. `최종판정`의 `enum`·`reason`은 결과가 검증된 뒤 별도 필드에 저장한다. `처리 완료 + 담당자확인`이면 워커는 다음 팀으로 넘어가고, 팀장 메일은 담당자가 원본을 확인하고 결론을 저장한 뒤 발송한다. 기술 실패만 발생한 건은 담당자의 운영 알림으로 남긴다.

## 5. 결과·발송 이력과 로그

팀 배정이 확정된 현재 버전의 유효한 결과를 받으면 하나의 DB 트랜잭션에서 추출값·판정·근거, 완료 상태와 담당자 알림을 기록한다. `재제출요청`은 확인된 사유를 한 통에 묶어 즉시 발송 대기시킨다. `담당자확인`은 담당자가 원본 대조 결론을 기록한 뒤 그 결과만 한 통, 보완본 통과는 완료 메일 한 통, 최초 정상은 예외 메일 0통이다. 발송 직전에도 팀 배정·현재 버전·해당 팀의 확인된 수신 주소를 확인한다. 주소가 불확실하면 담당자에게 표시하고 주소 확인 후 현재 결과만 보낸다. 대회·팀·제출 버전·안내 종류에 고유 조건을 두어 반복 조회·재시작으로 중복 발송하지 않는다. 메일 전송 응답이 끊기면 이력을 대조해 미발송만 재시도하고, 교체된 버전의 대기 메일은 건너뛴다.

운영 로그에는 시각, 접수번호, 팀 내부 ID·버전, 단계, `job_id`(생성 전은 빈 값), 파일의 안전한 표시명, HTTP 상태·정제한 오류 코드와 설명, 시도 횟수·다음 시각을 남긴다. 예를 들어 `파일02.hwpx`를 기록하고 실제 원본 파일명은 접수 상세에서 대조한다. 이름·학번이 든 파일명, 계좌·주민번호, 원본 내용, 메일 본문, API 키나 외부 응답 전문은 로그에서 제외한다. 담당자 화면에는 대기 팀 수와 가장 오래 기다리는 팀의 접수 시각, 실패 단계와 가능한 조치를 표시한다.

운영판 제출 상세 API의 `audit[]`는 각 시도의 `http_status`와 `error_code`를 반환한다. 요청 한도 초과는 `429 / RATE_LIMITED`, 일시적 서비스 중단은 `503 / SERVICE_UNAVAILABLE`, 응답 없는 타임아웃은 `null / TIMEOUT`이다. 팀 검토 화면의 **제출 버전과 기록**에서도 확인할 수 있다. 기존 이력에서 수집하지 않은 값은 `null`이다.

### 5.1 담당자 Gmail 연결

운영 데이터 폴더의 Gmail 프로필에는 담당자 주소를 지정한다. 새 PC에서는 서버 환경에 `MAIL_MODE=gmail`과 `GMAIL_ADDRESS`를 설정해 처음 연결할 주소를 지정할 수도 있다. 한 팀이 보완 대상이면 담당자와 팀장에게 각각 한 통을 예약한다. 원본 대조가 필요한 팀은 먼저 담당자에게만 보내고 담당자가 결론을 저장하면 팀장에게 한 통을 보낸다.

1. 담당자 계정으로 Google Cloud에서 프로젝트를 만들고 상단에서 그 프로젝트를 선택한다. Gmail API의 **사용**을 누른다. [프로젝트 만들기](https://console.cloud.google.com/projectcreate) · [Gmail API](https://console.cloud.google.com/apis/library/gmail.googleapis.com)
2. **Google 인증 플랫폼 → 브랜딩 → 시작하기**에서 앱 이름, 사용자 지원 이메일, 대상 **외부**, 연락처 이메일을 입력하고 만든다. **대상 → 테스트 사용자 → 사용자 추가**에 담당자 주소를 저장한다. **데이터 액세스 → 범위 추가 또는 삭제**에서 메일은 `gmail.send`, 로그인 주소 확인은 `openid`와 `userinfo.email`을 사용한다. 외부 앱이 테스트 게시 상태이면 Gmail 권한의 갱신 토큰은 7일 후 만료되므로 지속 운영 전 게시 상태와 Google의 앱 요건을 확인한다. [대상 설정](https://console.cloud.google.com/auth/audience) · [Gmail 권한](https://developers.google.com/workspace/gmail/api/auth/scopes) · [Google 토큰 만료 기준](https://developers.google.com/identity/protocols/oauth2#expiration)
3. [Google 인증 플랫폼 → 클라이언트](https://console.cloud.google.com/auth/clients)에서 기존 **웹 애플리케이션**을 열거나 새로 만든다. **승인된 리디렉션 URI**에 `http://127.0.0.1:18765/api/settings/gmail/callback`을 정확히 추가한다. Windows 시연판도 쓰면 기존 `http://127.0.0.1:8765/api/settings/gmail/callback`을 함께 둔다. 다른 호스트에 배포할 때는 서버의 `AWARDS_GMAIL_REDIRECT_URI`와 Google 설정 양쪽에 동일한 공개 HTTPS 콜백 주소를 지정하고 담당자도 그 호스트로 접속한다. [Google의 클라이언트 생성 안내](https://developers.google.com/workspace/guides/create-credentials)
4. [운영판 Gmail 연결](http://127.0.0.1:18765/#/gmail)에서 **Google로 연결**을 누르고 담당자 계정의 **이메일 보내기**를 승인한다. 승인하거나 취소하면 같은 탭의 Gmail 연결 화면으로 돌아온다. Spring Boot는 담당자 로그인 세션, 일회용 요청 값과 PKCE를 확인하고, 발송 권한과 인증된 이메일 주소가 일치한 경우에만 갱신 토큰을 교체한다. 앱 비밀번호 방식도 같은 화면에서 설정할 수 있다. [Google 웹 서버 인증](https://developers.google.com/identity/protocols/oauth2/web-server) · [Google 앱 비밀번호 안내](https://support.google.com/accounts/answer/185833?hl=ko)
5. **팀별 서류 검토 → 팀장 수신 주소 확인**에서 원접수 주소 한 개를 저장한다. 학교·네이버·다음·Gmail 등 도메인과 관계없이 사용할 수 있다. 연결 전에는 대기하고, 연결 후에는 해당 팀의 현재 버전만 처리한다. `발송 접수`는 메일 서버가 메시지를 받아들인 상태다. 도착은 수신함에서 확인한다. 별도 테스트 데이터 폴더에서 `MAIL_MODE=local`을 지정하면 로컬 메일함으로 시험할 수 있다.

운영판에서 **연결 해제**를 누르면 서버가 Google에 갱신 토큰 철회를 요청한다. 철회가 확인되면 발송 프로필에서 토큰을 지우고, 재연결용 웹 클라이언트 설정만 Windows DPAPI로 보호해 보관한다. 담당자는 **Google로 연결**로 다시 승인할 수 있다. Google이 일시적으로 응답하지 않으면 화면에서 해제를 다시 시도한다. [Google 권한 철회](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke)

이 PC에서 두 서비스는 같은 Windows 사용자와 `AWARD_DATA_DIR`(기본: 프로젝트의 `var`)을 사용한다. Spring Boot는 기존 Google 연결이 있으면 DPAPI로 암호화된 프로필에 있는 클라이언트를 재사용한다. 최초 설정이나 클라이언트 교체 때만 서버 환경에 `GMAIL_ADDRESS`와 `AWARDS_GMAIL_CLIENT_FILE`(웹 클라이언트 JSON의 절대 경로)을 지정한 뒤 재시작한다. JSON은 저장소 밖에 보관한다. 18765의 계정 상태 조회·Google 승인·앱 비밀번호 설정은 8765가 꺼져 있어도 된다. 운영판 워커는 PostgreSQL과 Spring Boot에 연결하며 `./start-intake.ps1`로 시작한다. 시연판은 `./start-service.ps1`과 별도의 SQLite 대기열을 사용한다.

## 6. 구현 순서와 인수 시험

먼저 가상 원본과 지연·실패를 제어할 수 있는 모의 API로 복구 동작을 확인한다. 실제 Agent ID와 테스트 메일함을 사용하는 연동 시험 결과는 별도로 기록한다.

| 순서 | 시험과 통과 기준 |
|---|---|
| 1. 접수·상태 API | set01 업로드 후 모의 AI 응답을 60초 늦춘다. 가상 자료 기준 마지막 바이트 수신부터 1초 이내에 원본·배정 작업이 저장되고 `202`와 일괄 조회 주소가 돌아오는지 측정한다. 화면을 닫았다 열어도 같은 건이 보인다. 선택한 원본의 전송 중단·디스크 저장 실패에는 판정 Job 0건이다. |
| 1a. 팀명이 없는 혼합 업로드 | 공식 set01·set02 사본의 파일명·폴더명에서만 팀명·세트 번호를 가리고 두 02를 같은 이름 `동의서.hwp`로 올린다. 02·03을 01보다 먼저 선택한다. 02 작성자 전원이 유일하게 일치해 Nextify 3명·AutoAI 4명으로 자동 배정되어야 한다. 소속 근거가 부족한 03은 원접수와 대조한다. 배정 후 팀당 원본 3개·판정 Job 1건씩, 교차 첨부 0건이다. 일부 명단은 set10으로 별도 시험해 해당 팀에 배정한 뒤에도 누락 사유가 남는지 확인한다. |
| 1b. 미배정과 실제 누락 | 가상 사본으로 동명 팀, 1인 동의서의 동명이인, 파일명 A팀·본문 B팀, 대표 이름만 있는 03, 두 팀이 섞인 PDF를 각각 시험한다. 후보·근거가 담당자 화면에 보이고 해결 전 관련 팀은 판정 Job·학생 메일·최종 집계 0건이다. A·B 공통 후보인 02를 B로 배정하면 B는 그 파일을 받고, 실제 02를 받지 않은 A만 누락 사유로 안내한다. 출처가 확정된 별도 팀은 먼저 처리한다. |
| 1c. 배정 정정·원문 검토 | 같은 배정 확인을 두 번 저장해도 팀별 버전과 작업은 하나다. 판정 후 발송 대기 중 파일을 다른 팀으로 옮기면 양쪽의 이전 발송과 집계는 보류되고, 수정한 현재 목록만 검토한다. 체크리스트에서 계좌 불일치는 01·03의 근거 쪽으로, 02 전체 누락은 확정 접수 목록으로 이동한다. |
| 2. 대기열·중복 | 서로 다른 세 팀을 이어서 접수해 접수 확정 순서와 원격 최대 동시 실행 1건을 확인한다. 같은 set01을 동시 재전송하고 `202` 응답 유실을 재현해 접수 1건·Job 1건인지 본다. 같은 파일명의 수정본은 새 버전, 다른 팀은 별도 접수, set05 유형은 중복된 두 파일 모두 입력이어야 한다. |
| 3. 장애·재기동 | 접수 확정 직후, Job 생성 응답 저장 전, `job_id` 저장 후에 각각 워커를 중단·재시작한다. 순서대로 기존 대기 작업 재개, 생성 여부 확인, 같은 ID 조회가 되어야 한다. 429·503·조회 타임아웃에는 간격·상한을, `failed`·손상 파일·권한 오류에는 다음 조치와 학생 메일 0통을 확인한다. 장기 실행 기준은 시험용 시계로 넘겨 새 Job을 만들지 않는지 본다. |
| 4. 판정·메일·버전 | set03의 계좌 불일치와 set10의 동의서 명단 누락에 각 팀별로 담당자 알림 1건과 팀장 메일 1통, 흐린 사본은 담당자 확인 전 0통·결론 후 1통이어야 한다. 결과 저장 직후 재시작해도 중복 발송이 없어야 한다. 이전 Job이 보완본 접수 뒤 완료되면 새 버전의 결과·메일·보고서에는 반영되지 않아야 한다. |
| 5. 실제 연동 | 실제 Agents API에서 set01과 set02가 각각 그 팀의 파일만 담은 Job으로 실행되는지, set04의 동의서 보완 안내가 확인한 테스트 메일함에 한 통 도착하는지 확인한다. 담당자가 확정한 버전·시상구분·지원액으로 편집 가능한 HWPX와 그 PDF를 만든다. 두 파일 모두 맨 앞의 00 두 표와 팀별 01→02→03 전체 원본이 한 번씩 같은 순서로 나와야 한다. |
| 5a. 운영판 보고서 출력·복구 | set01·02의 HWPX를 생성하고 전용 PC에서 출력해 11쪽 기준본과 표·서명·이미지 위치를 대조한다. 시상구분 한 셀을 바꾼 HWPX를 다시 올리면 새 PDF에 그 값이 반영되어야 한다. 서로 다른 두 담당자가 요청한 뒤 출력 중 전용 PC를 재부팅해도 각자 자신의 같은 버전 파일 한 쌍을 받아야 한다. |

| 메일 | set04의 팀장 보완 메일 한 통과 별도 담당자 알림 한 통을 로컬 메일함의 수신 주소·한글 제목·본문으로 확인했다. 재조회와 워커 재실행으로 같은 안내가 증가하지 않았다. |
| 공식 오류 사례 | set03·05·10의 한글을 로컬 판독하고 통제한 Studio 응답을 적용했다. set03의 계좌 확인은 01·03 원본으로 연결됐다. set05는 01 한 부·02 두 부·03 미제출이었다. set10은 신청서 3명 중 동의서 2명, 학부·학과 표기 차이가 있어 원접수 대조 후 배정했다. 세 팀 모두 누락·불일치 항목을 한 통으로 묶었다. |
| 권한·접수 응답 | PostgreSQL HTTP 회귀 시험 21건이 통과했다. 동일 작업 동시 배정, 보완·재배정 시 버전 분리, 권한 없는 원본 주소 거부가 포함된다. 60초 모의 판정 중 공식 set01의 마지막 바이트 전송부터 202 응답까지 0.275~0.279초였다. |
| 장애 복구 | 생성 응답 유실, 실행 ID 연결, 429와 Retry-After, 503·조회 타임아웃, 권한 오류, 잘못된 결과와 실패 종료 후 재개를 모의 응답으로 확인했다. 새 보완본이 도착한 뒤 끝난 이전 실행은 메일을 만들지 않았다. 보완 성공은 팀장 완료 안내 한 통, 별도 신규 접수의 정상 판정은 예외 안내 0통이었다. |
| 보고서·재기동 | 두 계정이 각각 자기 보고서만 확정·다운로드했다. 기본 지급값 기준 11쪽 전체, 실제 검토값 보고서는 증빙 9쪽 전체가 기존 편철 기준본과 120dpi에서 일치했다. 증빙의 쪽 크기·텍스트·내장 이미지도 단독 원본과 대조했다. 인쇄 프로세스를 HWPX 수신 직후 종료하고 시험 임대를 만료시키자 새 프로세스가 동일 버전을 출력했다. 시상구분 한 셀을 편집한 새 HWPX는 업로드한 바이트가 보존됐고 PDF 첫 쪽에 수정값이 반영됐다. 로컬 HTTPS 시험 서버에서도 인증서 확인·출력 전용 토큰으로 HWPX 전송부터 실제 11쪽 PDF 반환과 확정까지 검증했다. |
| 브라우저 | Chrome의 데스크톱·모바일 폭에서 두 계정으로 팀 검토 원문, 메일 이력과 확정 파일을 열었다. 로그아웃 상태의 보고서 다운로드는 401, 같은 대회 다른 담당자의 보고서 URL은 404였다. |
| 수동 확정 시점 | 공식 set04 원본 두 개를 먼저 팀에 배정했다. 검토 PDF가 0개, 1개, 2개여도 배정 근거 처리가 끝나기 전에는 수동 확정이 409였고 제출본·작업은 0건, 워커 수령 응답은 204였다. 준비 상태가 `ready`가 된 뒤 두 번 확정하자 같은 제출본과 작업 한 건을 반환했다. |
| 근거별 원문·누락 목록 | 공식 set03·04·05·10을 한글에서 판독하고 통제한 Studio 응답으로 검토 화면을 열었다. Chrome에서 set03의 01·03 계좌 근거, set05의 동의서 두 부, set10의 명단 근거를 각각 눌러 원본 파일과 PDF 쪽을 대조했다. set04의 동의서 0부 항목은 해당 버전의 확정 원본 두 개를 표시했고 목록에서도 원문을 열었다. |
| 재시도 이력 | 같은 원격 작업 조회에서 429 → 503 → 타임아웃 → 429를 재현했다. PostgreSQL에 저장한 이력을 상세 API로 다시 읽어 HTTP 상태, 오류 코드, 횟수와 원격 작업 ID를 확인했다. 최종 처리 후에도 Chrome에서 429와 503 기록을 각각 열람했다. |

지급내역의 시상구분은 대상·최우수상, 지원액은 각각 10만 원으로 시험 담당자가 입력했다. 원본 입력을 유지하면서 보고서 금액과 상명 편집을 검증하기 위한 값이다.

실제 Studio 시험은 `AWARDS_LIVE_ACCEPTANCE=1`로 실행한다. `tests/test_operations_acceptance.py`는 공식 ZIP, 기준 PDF, 한글, 시험 계정 두 개와 `MAIL_MODE=local`을 사용한다. 기준 PDF를 다른 위치에 보관하면 `AWARDS_ACCEPTANCE_REFERENCE`에 경로를 지정한다. 동일 시험을 이어갈 때는 해당 시험 대회의 UUID를 `AWARDS_ACCEPTANCE_EVENT`에 지정해 이미 받은 Studio 결과를 재사용한다. 로컬 오류 사례는 별도의 빈 DB에서 `AWARDS_OFFLINE_CASES=1`로 `tests.test_operations_cases`, 모의 복구 시험은 또 다른 빈 DB에서 `AWARDS_RECOVERY_TESTS=1`로 `tests.test_operations_recovery`를 실행한다. 학교 전용 PC의 실제 재부팅과 학교 한글 계약의 무인 사용 범위는 현장 확인 항목이다.
